# Larder — план имплементации

Живой документ. Статус каждой задачи обновляется **в том же PR**, который её выполняет.
Контекст продукта: [VISION.md](VISION.md) · экраны: [DESIGN_BRIEF.md](DESIGN_BRIEF.md) и [design/](design/) · правила работы: [CLAUDE.md](CLAUDE.md).

## Как вести план

- Одна задача = одна ветка = один PR. Ветка: `feat/<id>-<slug>` (например, `feat/2.1-cart-model`), для инфраструктуры — `chore/...`, для багов — `fix/...`.
- PR обязан обновить строку своей задачи и, при изменении поведения/env/настройки, страницы в `docs/wiki/`.
- **Конвенция статусов** (main защищён, мерж не редактирует файлы — поэтому так): при старте работы первый коммит ветки ставит строке 🔵; последним коммитом перед мержем PR ставит своей строке 🟢 и номер PR (строка опережает мерж на минуты — приемлемо; если PR закрыт без мержа, следующий PR возвращает ⬜). ⛔ с причиной проставляется ближайшим PR.
- Порядок фаз — это порядок зависимостей: фазу N+1 не начинаем, пока не смержены блокирующие задачи фазы N (помечены ⚑).
- Распределение моделей: оркестрация, планирование, архитектурные решения и ревью — **Fable** (основная сессия); реализация задач делегируется сабагентам: `opus` — сложные, `sonnet` — простые. Метка стоит у каждой задачи.

**Статусы:** ⬜ не начато · 🔵 в работе (есть ветка/PR) · 🟢 смержено · ⛔ заблокировано

## Definition of Done (для каждой задачи)

1. Код соответствует правилам [CLAUDE.md](CLAUDE.md) (TS strict, Zod на границах, строки UI через next-intl).
2. Бизнес-логика покрыта тестами (vitest); парсеры — тестами на фикстурах.
3. CI зелёный: lint, typecheck, тесты, build.
4. Все комментарии CodeRabbit отработаны (исправлено или аргументированно отклонено) и треды зарезолвлены.
5. Строка задачи в этом файле обновлена; `docs/wiki/` актуализирована при необходимости.
